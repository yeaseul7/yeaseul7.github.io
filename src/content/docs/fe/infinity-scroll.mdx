## 문제: 페이지를 나눠 받아도 화면은 계속 커졌다

보호동물 목록에서 처음 30개를 불러오고, 화면 맨 아래에 도달하면 다음 30개를 추가했다. 네트워크 요청은 페이지 단위였지만, 이미 받은 카드는 화면에 계속 남아 있었다. 스크롤을 이어가던 중 크롬 탭에서 OOM(Out Of Memory)이 발생했다.

당시 선택한 대응은 **목록 가상화(Virtual List)** 였다. 핵심은 데이터를 가져오는 양과 DOM에 렌더링하는 양을 각각 제어하는 것이다.

## 관찰과 원인 가설을 구분하기

기존 구현에서는 데이터를 누적하면서 DOM 노드도 늘어났다. 이 구조는 메모리 사용과 렌더링 부담이 커질 수 있는 원인이지만, 오류 화면만으로 OOM의 원인을 DOM 하나로 확정할 수는 없다. 이미지 디코딩 메모리, 데이터 캐시, 해제되지 않은 참조도 함께 살펴봐야 한다.

| 구분 | 이 기록에서 확인할 수 있는 내용 |
| --- | --- |
| 관찰 | 30개씩 추가하는 목록에서 크롬 탭 오류가 발생했다. |
| 원인 가설 | 누적된 카드 DOM과 관련 리소스가 메모리 부담을 키웠다. |
| 적용한 대응 | 전체 목록 대신 화면 주변의 셀만 렌더링하는 가상화를 도입했다. |
| 검증 한계 | 당시의 힙 스냅샷, DOM 노드 수, 개선 전후 메모리 측정값은 이 글에 남아 있지 않다. |

따라서 이 글은 가상화를 선택한 이유와 구현 원리를 설명한다. OOM의 단일 원인을 입증하거나, 메모리 감소율과 재발 방지를 검증한 결과로 읽어서는 안 된다.

## 가상화가 줄이는 것

일반 목록은 받은 데이터가 늘어날 때마다 카드 DOM도 늘어난다. 가상화는 전체 데이터의 위치를 계산하되, 화면에 보이는 행과 주변의 여유 영역만 렌더링한다. [react-window 1.x의 설명](https://github.com/bvaughn/react-window/tree/1.8.11)도 DOM의 과도한 할당을 줄이는 것을 주요 효과로 제시한다.

고정 높이 그리드에서는 두 요소의 역할을 나누면 이해하기 쉽다.

- **Outer Element:** 지정한 `height`를 가진 실제 스크롤 컨테이너다. 여기서 `scrollTop`을 읽는다.
- **Inner Element:** 전체 행 수에 해당하는 높이를 확보한다. 전체 높이는 `rowCount × rowHeight`이며, 셀은 계산된 위치에 배치된다.

`scrollTop / rowHeight`로 보이는 행의 위치를 계산하고, 해당 범위 주변만 DOM으로 만든다. `overscanRowCount`는 빠른 스크롤 때 빈 영역이 보이는 현상을 줄이려고 추가하는 여유 행이다. 값을 크게 잡을수록 렌더링하는 셀도 많아진다.

**가상화는 데이터 배열을 자동으로 비우지 않는다.** 카드를 화면에서 제거하더라도 모든 API 응답을 배열에 보관하면 그 데이터는 메모리에 남는다. 장시간 탐색에서는 데이터 보관 범위와 이미지 처리도 별도로 설계해야 한다.

## 구현 예시: 화면 크기와 로딩 상태를 함께 전달하기

다음은 원래 구현의 아이디어를 정리한 **미실행 예제**다. `react-window 1.x`의 `FixedSizeGrid` API를 기준으로 하며, 서비스 전체 코드를 옮긴 것은 아니다. 설치된 버전이 다르면 해당 버전의 API를 확인해야 한다.

```tsx
import { useMemo } from "react";
import { FixedSizeGrid as Grid, type GridChildComponentProps } from "react-window";

type Item = { id: string; title: string };
type CellData = { items: Item[]; columnCount: number };
type Props = {
  items: Item[];
  width: number;
  height: number;
  isLoading: boolean;
  hasNextPage: boolean;
  onLoadMore: () => void;
};

const ROW_HEIGHT = 240;
const LOAD_MORE_THRESHOLD = ROW_HEIGHT * 2;

function Cell({ columnIndex, rowIndex, style, data }: GridChildComponentProps<CellData>) {
  const item = data.items[rowIndex * data.columnCount + columnIndex];
  if (!item) return null;
  return (
    <div style={style}>
      <article>{item.title}</article>
    </div>
  );
}

export default function VirtualizedGrid({
  items, width, height, isLoading, hasNextPage, onLoadMore,
}: Props) {
  const columnCount = width < 640 ? 1 : 3;
  const rowCount = Math.ceil(items.length / columnCount);
  const itemData = useMemo(() => ({ items, columnCount }), [items, columnCount]);

  return (
    <Grid<CellData>
      width={width}
      height={height}
      columnWidth={width / columnCount}
      columnCount={columnCount}
      rowHeight={ROW_HEIGHT}
      rowCount={rowCount}
      itemData={itemData}
      overscanRowCount={2}
      itemKey={({ columnIndex, rowIndex, data }) =>
        data.items[rowIndex * data.columnCount + columnIndex]?.id
          ?? `empty-${rowIndex}-${columnIndex}`
      }
      onScroll={({ scrollTop }) => {
        const nearEnd = scrollTop + height >= rowCount * ROW_HEIGHT - LOAD_MORE_THRESHOLD;
        if (nearEnd && hasNextPage && !isLoading) onLoadMore();
      }}
    >
      {Cell}
    </Grid>
  );
}
```

셀에는 라이브러리가 전달한 `style`을 적용해야 위치 계산이 반영된다. 카드 내부의 이미지와 텍스트도 정한 행 높이 안에 들어가도록 구성해야 한다.

`width`와 `height`는 부모가 측정해서 전달한다. 최초 데이터 로딩과, 목록이 짧아 스크롤이 생기지 않는 경우의 추가 로딩도 부모에서 처리해야 한다. `isLoading`이 갱신되기 전 여러 콜백이 실행될 수 있으므로, 요청 함수나 데이터 조회 계층에서도 동일 페이지의 중복 요청을 막아야 한다.

## 다시 검증한다면 무엇을 측정할까

아래 절차는 **후속 검증 방법이며, 이번 글 보강에서 실행한 실험은 아니다.** 같은 기기·브라우저·데이터·뷰포트에서 일반 목록과 가상화 목록을 비교해야 한다.

1. 같은 30개 단위 데이터와 이미지로 시작해, 정해진 횟수만큼 다음 페이지를 불러온다.
2. 각 구간에서 로드한 항목 수와 실제 카드 DOM 수를 함께 기록한다. 가상화에서는 화면 크기가 같다면 카드 DOM 수가 전체 항목 수에 비례해 계속 늘지 않는지 확인한다.
3. [Chrome DevTools의 메모리 분석 도구](https://developer.chrome.com/docs/devtools/memory-problems)로 JS 힙, DOM 노드, 브라우저 메모리의 추세를 함께 살핀다. 강제 GC를 사용한다면 양쪽에서 같은 시점에 수행한다.
4. 화면을 떠난 뒤에도 사용량이 계속 남는다면 힙 스냅샷에서 참조 관계와 분리된 DOM을 조사한다. 가상화 적용 여부만으로 누수를 판단하지 않는다.
5. 반복 스크롤에서 오류 재발 여부와 중복 요청도 확인한다. DOM 감소와 사용자 문제 해결은 각각 검증한다.

기록에는 브라우저 버전, 기기, 데이터 개수, 측정 시점과 단위를 함께 남겨야 한다. JS 힙 수치 하나만으로 이미지나 탭 전체 메모리가 얼마나 줄었는지 결론 내리지는 않는다.

## 적용 조건과 남은 한계

| 선택 | 적합한 상황 | 추가로 고려할 점 |
| --- | --- | --- |
| 페이지 이동 | 한 번에 보여줄 양을 명확하게 제한할 수 있다. | 페이지 전환과 탐색 경험을 설계해야 한다. |
| 일반 무한 스크롤 | 누적되는 항목이 적고 카드가 가볍다. | 장시간 탐색에서 DOM과 데이터가 계속 늘 수 있다. |
| 가상화한 무한 스크롤 | 큰 목록에서 연속 탐색이 필요하다. | 높이 계산, 포커스 유지, 스크린 리더와 브라우저 내 찾기 동작을 확인해야 한다. |

이 사례에서 가상화를 선택한 이유는 연속 탐색을 유지하면서 렌더링 범위를 제한하기 위해서였다. 다만 가상화는 메모리 관리 전체를 대신하지 않는다. **페이지 단위 요청, DOM의 렌더링 범위, 데이터의 보관 범위를 나눠서 관리하는 것**이 이 문제에서 얻은 핵심이다.
