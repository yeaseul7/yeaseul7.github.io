## 배경: 배포 위치보다 실행 책임을 먼저 나누기

Vercel로 배포하던 프로젝트의 구조가 커지면서 요금 정책과 실행 환경의 제약을 다시 살펴보게 됐다. 기존 기록에서 선택한 방향은 프론트엔드와 Edge에 남길 코드, Node.js 의존성이 큰 AI 처리, 데이터 접근의 책임을 나누는 것이었다.

이 글은 당시의 설계 기록을 바탕으로 선택 이유와 한계를 보강했다. **기존 기록의 배포 경험과, 현재 공식 문서에서 확인한 플랫폼 동작을 구분한다.** 당시 청구서·동일 조건의 벤치마크·번들 분석 로그는 이 글에 첨부되어 있지 않으므로 정량적인 비용 절감이나 성능 향상을 입증하는 자료로 보기는 어렵다.

## 무엇을 기준으로 비교했나

요금만 보고 플랫폼을 선택하면, 이전 후 발생하는 호환성 문제나 운영 비용을 놓치기 쉽다. 이 사례에서 다시 확인해야 할 기준은 네 가지다.

| 기준 | 확인할 질문 |
| --- | --- |
| 실행 환경 | 사용하는 SDK가 필요한 Node.js API와 의존성을 지원하는가? |
| 배포 제약 | 번들 크기, 초기화 시간, 메모리와 실행 시간에 맞는가? |
| 비용 | 요청·연산뿐 아니라 DB·저장소·네트워크·운영 비용까지 포함했는가? |
| 권한 경계 | 브라우저, Edge, 백엔드가 각각 어떤 데이터와 비밀 키에 접근하는가? |

Vercel이 Node.js를 지원한다는 사실만으로 더 비싸다고 설명할 수는 없다. [Vercel Functions도 실행 환경을 구분](https://vercel.com/docs/functions/runtimes)하며, 어느 쪽이 유리한지는 기능과 사용량을 함께 놓고 판단해야 한다. 이 글에서는 특정 플랫폼이 언제나 저렴하다는 결론을 내리지 않는다.

## Edge로 옮길 때 드러나는 호환성 문제

Cloudflare Workers에서는 전체 Node.js 환경과 동일하게 동작한다고 가정하면 안 된다. [공식 호환성 문서](https://developers.cloudflare.com/workers/runtime-apis/nodejs/)는 기본 제공 API, 부분 구현, 폴리필을 구분한다. 모듈 import에 성공해도 실제 호출 경로까지 실행해서 확인해야 한다.

따라서 Node.js 의존성이 큰 AI SDK를 그대로 Edge에 포함하기보다, 해당 로직을 별도 백엔드로 분리하는 선택을 했다. 여기서 중요한 것은 “AI 기능은 Edge에서 실행할 수 없다”는 일반화가 아니다. **현재 의존성이 요구하는 기능과 실행 환경이 맞는가**를 확인하는 것이다.

### 번들 크기 제한은 당시 조건과 현재 조건을 나누기

초기 글에서는 `3 MiB`를 제약으로 언급했다. 하지만 당시 플랜과 배포 로그를 함께 남기지 않았으므로 이를 현재의 공통 제한으로 안내할 수는 없다.

2026년 11월 25일 확인한 [Workers 제한 문서](https://developers.cloudflare.com/workers/platform/limits/#worker-size)는 Free·Paid 모두 **비압축 Worker 크기 64 MiB**를 안내하고 있으며, 압축 크기를 제한 기준으로 삼지 않는다. 이 값은 정적 자산이나 다른 제품의 제한과 구분해야 하고, 실제 적용 시점에 다시 확인해야 한다.

번들 크기가 허용 범위 안에 있더라도 초기화 시간과 런타임 호환성 문제가 남을 수 있다. SDK 분리를 판단할 때는 크기뿐 아니라 실제로 실행하는 경로를 함께 확인해야 한다.

## 선택한 구조: AI 처리와 화면 제공 분리

기존 기록에서는 AI 로직을 **Google Cloud Run의 컨테이너 서비스**로 분리하고, 프론트엔드·Edge 쪽에서 REST API로 호출하도록 바꿨다. Node.js에 강하게 묶인 SDK를 Edge 번들에서 걷어내면서 Cloudflare 배포가 가능해졌다고 기록했다.

[Cloud Run](https://docs.cloud.google.com/run/docs/overview/what-is-cloud-run)은 컨테이너 기반 서비스를 운영할 수 있는 실행 환경이다. 이 사례에서 그 역할은 AI 처리의 의존성과 실행 환경을 Edge 배포에서 분리하는 것이었다. 컨테이너로 옮겨도 실행 제한과 운영 책임은 계속 확인해야 한다.

| 계층 | 맡긴 책임 | 분리로 생기는 비용과 한계 |
| --- | --- | --- |
| 프론트엔드·Edge | 화면 제공과 필요한 API 호출 | 백엔드 장애와 지연에 대응해야 한다. |
| Cloud Run | Node.js 의존성이 큰 AI 처리 | 네트워크 호출, 인증, 타임아웃, 관측이 추가된다. |
| 데이터 계층 | 데이터 조회·저장과 접근 제어 | 캐시 일관성과 요청 주체별 권한을 관리해야 한다. |

분리는 배포 호환성 문제를 줄이는 대신 서비스 간 호출을 추가한다. 가까운 실행 위치, 요청 크기, 연결 재사용, 재시도 정책에 따라 지연과 비용이 달라질 수 있으므로, 이전만으로 응답 속도까지 개선됐다고 단정할 수는 없다.

## 데이터 비용: 읽기를 줄여도 총비용은 따로 계산하기

기존 기록에는 Cloud Storage에 메타데이터를 두고 캐싱해서 Firestore 읽기를 줄이는 접근이 등장한다. 반복해서 필요한 데이터를 캐시로 제공하면 DB 조회를 줄일 여지가 있지만, 데이터 갱신과 캐시 무효화의 책임이 생긴다.

이 선택을 평가할 때는 다음을 함께 확인해야 한다.

- 어떤 데이터를 캐시하며, 사용자별 접근 권한을 어떻게 보존하는가?
- 원본 변경을 언제 반영하며, 오래된 데이터를 얼마나 허용하는가?
- 캐시 실패나 만료 시 DB 조회가 한꺼번에 몰리지 않는가?
- 줄어든 DB 읽기 비용보다 저장소 요청·전송·운영 비용이 커지지는 않는가?

Firestore를 사용할 때의 설계 기준은 [공식 모범 사례](https://firebase.google.com/docs/firestore/best-practices)에서도 확인할 수 있다. 이 글에서는 다른 저장소로 일부 요청을 옮겼다는 사실만으로 총비용이 줄었다고 결론 내리지 않는다.

초기 기록에 있던 **Firestore 비용 약 95%, 번들 약 90% 관련 수치**는 비교 기간·원본 수치·산식이 없어 재검증할 수 없다. 특히 번들이 “기존의 90%가 됐다”와 “90% 감소했다”는 서로 다른 의미다. 이번 보강에서는 이 수치를 검증된 성과로 사용하지 않는다.

## Data API와 권한 경계

기존 기록에서는 Data API를 사용하고, 브라우저와 백엔드의 키를 분리했다고 적었다. 여기서 **키를 나누는 것과 실제 접근을 제한하는 것은 별개의 작업**이다.

테이블·스키마를 API에 노출할지, 어떤 역할에 권한을 줄지, 그 역할이 어떤 행을 읽고 수정할 수 있을지를 각각 설정해야 한다. 예를 들어 [Supabase의 RLS 설명](https://supabase.com/docs/guides/database/postgres/row-level-security)은 행 단위 정책과, 정책을 우회할 수 있는 서비스 역할 키를 구분한다. RLS를 켰다는 사실만으로 모든 호출 경로가 안전해지는 것은 아니다.

브라우저에는 공개 가능한 클라이언트 키만 전달하고, 비밀 키는 서버에 보관해야 한다. 서버가 높은 권한으로 실행한다면 요청 사용자의 인증·인가도 별도로 확인해야 한다. 이 내용은 설계 검토 기준이며, 이 글에서 현재 운영 환경의 권한 설정을 감사했다는 의미는 아니다.

## 다음 검증에 남겨야 할 근거

아래는 **추가로 실행해야 할 비교 항목**이다. 이번 글 보강에서 새로 측정한 결과는 아니다.

| 항목 | 남길 근거 | 판단 기준 |
| --- | --- | --- |
| 번들 | 같은 기능·빌드 조건의 이전·이후 배포 로그 | 어떤 의존성이 얼마나 빠졌는가? |
| 호환성 | 실제 AI·DB·인증 요청 경로의 실행 결과 | import뿐 아니라 기능 호출도 성공하는가? |
| 지연·안정성 | 같은 부하에서의 응답 시간 분포와 오류율 | 추가 호출과 초기 실행이 사용자 경험에 미치는 영향은? |
| 총비용 | 같은 사용량 기준의 플랫폼·DB·저장소·전송 비용 | 한 계층의 절감이 다른 계층의 증가로 상쇄되는가? |
| 접근 제어 | 익명·일반 사용자·서버 역할별 허용·거절 결과 | 다른 사용자의 데이터에 접근할 수 없는가? |

플랫폼별 트래픽과 기능이 다르면 청구서 합계만 비교해서는 이전 효과를 분리하기 어렵다. 비교 기간, 요청 수, 데이터 크기와 캐시 조건을 함께 남겨야 한다.

## 이 선택이 적합한 조건

이 사례의 핵심은 호스팅 서비스를 바꾸는 데서 끝나지 않고 **Edge와 컨테이너의 책임을 다시 나눈 것**이다. Node.js 의존성을 별도로 운영할 이유가 분명하고, 추가 호출과 운영 부담을 감당할 수 있을 때 검토할 만한 구조다.

반대로 현재 환경에서 요구사항을 충족하고 있다면, 운영 대상을 늘리는 비용이 더 클 수 있다. 다음에 같은 선택을 한다면 배포 가능 여부에 더해 비용·지연·오류율의 비교 근거를 먼저 정하고, 그 근거를 기준으로 이전 효과를 평가하려 한다.
